## v1.0.2：退群后黄色提醒与两步确认修复（2026-10-18）

### 最简单的操作

在「群组管理」筛选「需核对名单」，列表会直接显示姓名和完整 ID。先在 Teams 核对仍能访问的群，再勾选群（可以全选当前筛选结果）→ 点击 **确认所选名单（X 群）** → 在唯一弹窗点击 **确定**。不再打开中间确认页，也不再要求额外勾选一段免责声明。每次最多处理 100 群；仍在群的名单需是最近 3 分钟内的完整缓存记录，若过期先点顶部 **立即检查**。

### 已退出群的特殊处理

如果在 Teams 退出群并在插件里手动标记退出（或被插件检测到退群），该群已有的黄色名单提醒**自动结束**，并保存当时的旧名单、候选名单、差异和审计记录。不会把退群前的旧缓存更新成可信名单，更不会批准陌生人；历史群数仍保留，但日常统计减 1。Teams 后续残留的退群聊天缓存不能重新触发该群的人员变化报警。已经在旧版中标记退出、但仍留下黄色提醒的群，也可以通过上述 **确认所选名单** 来清除，**无需再次核对当前已无法访问的人员名单**。

如果出现「未知操作」：通常是新版安全中心页面仍连接到旧后台脚本或扩展目录未完全覆盖。新版会提示到 `chrome://extensions` 点扩展 **重新加载**，然后刷新安全中心以及 Teams 网页。不要先卸载旧扩展，否则本地数据可能丢失。先从「设置与备份」导出备份。

**数据限制**：本地缓存差异不能证明谁真的加入或退出，也不能证明邀请人身份。退群标记是用户声明或 Teams 网页操作推断，不是微软服务器实时确认。版本号固定 **1.0.2**，未增加额外权限。

## v1.0.2 群组批量工作台（同版本持续改进）

安全中心 → 群组管理：

- 无须打开抽屉，直接在每个群卡片看到本地缓存**疑似新增、疑似缺少**的人员姓名和完整 Teams 成员 ID（姓名须有 ID 元数据或人工备注，不能靠群标题顺序臆测）。已有事件中的首次观察/历史核查差异也可显示，显示对应的观察时间与证据类型。
- 可直接筛选「待核查」「缓存疑似新增」「缓存疑似缺少」「缓存质量问题」「已记录退群」；搜索同时覆盖候选 ID 及其已关联姓名。
- 勾选、全选**当前筛选结果**、取消勾选；单次最多 500 群。批量设为重点守护、普通监控或安静记录。
- 如已在 Teams **逐一确认本人退出或重新加入**，可批量标记退群或撤销本地标记，要求两次人工确认。不会自动删除历史群组，也不会修改人员的信任状态；标记本人退出会结束该群已存在的黄色名单提醒并保留完整历史。
- 人员审核页也支持全选当前最多 150 名可见人员；事件、人员、群组关系尽可能显示完整 ID，方便直接核对。

**重要限制**：本地缓存出现/缺少某个 ID 不能证明此人实际加入/退出，更无法证明是谁邀请或移除了成员。黄色提醒可以在实际逐群核对后一次确认多群名单，不能在没有核实前直接消除。即便确认名单，插件也不会自动批准陌生人员。Teams 实际界面退群事件识别仍属于尽力识别，并非微软服务器实时成员资格证明。

# TeamsGroupSentry 1.0.2

Chrome MV3：本地群成员观察、身份审核与当前聊天请求警示。

## 退群统计（公开版本固定为 1.0.2）

弹窗主数字为“未标记退群”，安全中心同时显示“已记录退出（含自动）”和“全部历史群组”。若历史群有 385 个，你在已索引的群里执行 Teams 官方「退出群聊」→确认退出，且插件成功观察到确认窗口随后消失、未见错误，则自动标记此群为已退出，主数字为 384，历史仍为 385。该数字**不是微软服务器确认的实时在群数**；升级前已经退出的历史群，若当时没有记录，无法逆推出状态，仍需人工补记；新操作需要 Teams 网页在前台运行。

自动操作：保持扩展启用、当前 Teams 标签页已成功巡检并绑定账号，然后在 Teams 群组侧栏进入相应群，打开群操作菜单→「退出群聊」→在官方确认框再次确认。大约 5 秒后重新打开插件查看主数字，近期识别结果会显示在统计下方。如果菜单未能定位唯一群 ID，弹窗会说明不能自动扣除；对话框按钮也兼容「确认」「确定退出」等表达。若未识别，可在安全中心 → 群组管理 → 群详情中人工补记。Teams 官方 UI 结构变化、菜单脱离了群 ID、找不到群记录、尚未完成绑定或巡检失败时，自动功能会保守地不扣数；并不能保证实时准确。黄色核查提醒属于成员名单差异，不能当作本人退群证据，确认退出会结束本群已存在的黄色提醒并保留审计，但不会把旧缓存名单当成真实最新名单。重新入群后可手动“撤销退群标记”。退群记录属于当前账号，不删群组、不删历史人员/事件、不更改成员白名单和预警规则；缓存依然出现该群也不自动恢复已退出状态。

## 当前请求以 Teams 界面为依据

**历史缓存不能单独成立一个“当前聊天请求”。** 只在 Teams 当前可见的请求入口非零徽标、可见请求列表或已核对的接受/阻止面板提供证据时显示当前请求警示。当前无这些界面证据就撤下该提示；不会因此接受/阻止请求、批准身份或删除审核历史。旧版由 CACHE 来源生成的会话提醒立即停止展示。

无可关联的当前请求行时不启动正文缓存读取；出现新会话键时独立触发定向检查。缓存只给同一当前可见请求会话补充正文，按完整会话键精确关联；不能把其他历史缓存、普通聊天未读数、旧隔离标记或本人消息混入。只有入口数字而没有会话键时，只提示数量与详情待获取，不根据缓存猜是谁。当前请求条数来自界面，不来自隔离缓存记录数。

这项防误报取舍也有覆盖边界：请求入口/列表/面板未渲染或不可见、Teams 改版或页面冻结/关闭时可能没有提示；不因缓存里存在记录继续警报，也不能声称不存在服务器端请求。

## 小栏末条，弹窗更多正文

- 收起状态栏按 1、2…列出当前已取得的请求摘要，每个会话只显示已取得的最近一条文字；展开栏也保持末条摘要。
- 点击扩展图标，在弹窗查看每个当前请求已取得的最多 10 条文字，各自保留作者，每条最多 300 字。会议名不是邀请者姓名，消息作者也不自动变成邀请者。
- 缓存只有 lastMessage 时只能补一条；已取得的可见预览消息不会再被这一条覆盖。缓存末条可作为小栏的最新已取得摘要，但不保证服务器实时最后一条；无可用缓存末条则显示当前已取得预览的末条。
- 仅展示已经取得的文字，不宣称完整历史，不解析未经核对的 messages 字符串，不自动滚动聊天、切换请求、预览、接受、阻止、回复或打开链接。离开可见请求列表后，不用旧缓存维持当前详情警示。

正文不可得立即提示请求，不等待正文。安全提示置于正文之前：

> 核实身份后再决定是否接受。
> 切勿共享账号信息或授权登录。
> 先点「预览他们的消息」查看，不要为看消息直接点「接受」。

如果尚未进入请求，在 Teams 打开「请求」→选中请求→点官方「预览他们的消息」。本实现不自动触发预览，也没有验证预览的已读回执或在线状态副作用。

## 显示与身份保护

中性深色背景、白色正文、红色请求边框/标题；关键安全提示使用独立浅黄底深色粗体，并放在正文前。展开栏底部导航固定显示，采用浅底深字，与正文滚动分开。「收起本次提醒」不接受请求或批准身份。

本人消息仍按已批准缓存范围下人工确认的完整本人 ID 排除，不按姓名排除同名他人。该排除不能把当前官方请求界面自动判断为已接受/无效。原群成员陌生 ID 审核、账号分区、单群绑定、本人查找、聊天跳转、加密备份及历史审计保持原规则；没有删除个人数据。

请求摘要只在当前页面/扩展会话中限量保存，不写长期人员/群/审核库或备份。原始会话 ID 和消息 ID 不发送到后台；标题/作者/文字按文本安全显示。账号仍使用独立 Chrome 资料，在同一文档切换微软账号后须刷新并核对。

## 调度边界

DOM 变化约 250ms 合并，5 秒补偿检查，缓存读取最长约 1.8 秒后放弃本轮。它们是本地参数，不是从对方发送起算的延迟保证。正文读取不阻塞先行界面提醒。实际新请求预览前缓存写入、真实 Chrome 安装后的端到端时延、直接入群邀请者均未完成现场验证。

## 安装或更新

1. 在原扩展「设置与备份」导出加密备份，分别保管不同 Chrome 资料的备份。
2. 解压安装 ZIP。Chrome 开发者模式需要加载含 manifest.json 的 TeamsGroupSentry 文件夹，不能直接加载 ZIP。
3. 更新时保留原扩展 ID 和原加载路径，将新版运行文件复制到原加载目录，在 chrome://extensions 点「重新加载」，再刷新 Teams。不要先卸载旧扩展、清除浏览器数据或重建人员库。
4. 新安装可用「加载已解压的扩展程序」。已有账号绑定不因本次更新而重置；首次绑定仍需核对本人完整 ID。

公开版本始终固定为 1.0.2；此次为同版本功能维护，使用独立内部构建标记确保升级前恢复点保护仍然有效；权限未增加。本轮未替换用户已安装扩展，未改动原始源码或个人数据库；Chrome 正式安装/更新后的端到端验收尚未完成。

## 只有一个群的新账号

新的独立 Chrome 用户资料，读到 1 个有效完整群、且只有一个 Teams 会话缓存时，可以在弹窗或安全中心首次绑定区选择/输入本人完整人员 ID。请核对完整 ID 并填写最后 6 位后确认；不会自动选择本人，不能仅凭姓名选择。完整 ID 必须实际出现在本次群名单中。显示候选以外的已观察 ID 也可手动填写。

这是一项本地人工声明，不是微软登录身份认证；单群本身无法自动识别哪个成员是本人。已加入可选的本地本人线索查找，不读取 Token；具体缓存可能没有支持的线索，尚未在测试新号验证命中。独立 Chrome 资料之间保持隔离，不支持借这个入口覆盖另一账号历史。不要在同一资料中将旧账号基线直接用于另一个账号。

确认后，原缓存范围、本人 ID 和初始群中的已知同群人仍能对应时，后续扫描及重启无需重绑；线索冲突时保持只读。旧账号的多群连续性规则没有放宽。无有效群或缓存不完整时仍不能建立身份基线，但通用请求变化提醒无需绑定即可使用。

绑定不会让未读取的请求发送者 ID 或消息正文自动出现。

## 候选姓名与本人 ID 查找

首次只读绑定现在也合并本轮资料缓存的姓名，按完整人员 ID 精确对应、按来源优先级处理；同名不合并，最高优先级姓名冲突时明确标记，缺姓名时显示尚未取得。不需要先绑定才能看到本次已取得的姓名。

点击「查找 / 刷新本人 ID」会重新读取本地资料，跳过可选姓名缓存的等待期限。只在缓存中确实存在符合支持形状的明确线索时，才显示一个「待你确认」的候选，包含姓名、完整 ID 和线索来源。手动名单默认收起，不按名称、头像或出现群数自动选人。推荐消失或变化时清除旧自动选择。

支持的可选线索探测：会话数据库名称后缀恰为完整人员 ID；同一账号缓存范围的资料记录明确标记本人；会话记录明确标为本人已发最后消息且提供发送者 ID。**这些是条件探测，不宣称当前 Teams 版本/你的账号一定存在这些字段或形状。** 不存在、不完整、多缓存、线索冲突或无法与本次人员名单对应时不推荐。明确冲突时保持只读，不能继续绑定或沿用旧账号。

自动推荐也必须核对完整 ID、尾号并明确确认，才能建立初始基线；不会批准群内其他成员。新线索与已经确认的本人 ID 不一致时保护旧记录。线索本身不是微软登录认证，仍须核对当前账号。

没有完成新号的实际自动识别命中验证，也没有因为添加这个查找器就取得陌生消息正文/发送者 ID。不能用虚构测试结果宣称已识别你的真实本人 ID。

### 姓名没有显示（公开版本仍为 1.0.2）

新版会优先使用与完整 Teams 成员 ID 一一对应的资料缓存姓名，并在姓名后来才同步到缓存时自动尝试补全。在「新人员审核」可点击「重新查找姓名」；如果 Teams 群成员名单已打开，插件也会尝试读取该页面中明确同时包含完整 ID 和姓名的可见成员行。

没有找到对应关系时会显示「姓名尚未找到」并保留完整 ID，不会根据名单顺序、姓名相似或群名称猜配，也不会自动批准待审核身份。部分 Teams 页面不向浏览器公开姓名与 ID 的对应关系，因此依然可能需要人工备注。


### 查看单个群最近人员变化（1.0.2）

安全中心 →「群组管理」→ 点击群名或「近期人员变化」，即可按 7 / 30 / 90 天或全部保存记录查看：插件发现的时间、人员姓名、完整 Teams ID、新名单多出来和少掉的人员。群列表有「近30天有变化」筛选与摘要。

**时间口径**：显示插件首次观察到某次缓存差异的本地时间，不是 Teams 服务器确认的入群/退群时间，不能证明谁邀请了谁。历史记录从插件当时实际保存的事件提取；旧版从未保存的变更无法追溯，关闭提醒不会删除已记录的历史。普通已处理事件沿用既有约 180 天的清理规则，不能将「全部保存记录」理解成永久完整日志。成员姓名与 ID 以已有可靠绑定为准，不会按姓名猜测身份。
