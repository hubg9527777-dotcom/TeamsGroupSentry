# TeamsGroupSentry v1.0.2（最新群组 UI 版）安全审核与修复报告

**审核日期：2026-11-01。公开版本始终保持 1.0.2。**  
**输入来源：**对话内最新 `TeamsGroupSentry-1.0.2-UI-source.zip`，不是较早的 NameLinkFix 或 GroupSearch60 压缩包。  
**审核边界：**压缩包内全部生产 JavaScript、manifest、HTML/CSS、Node 测试、Python 打包脚本、文档和配置；**不包含**实际 Chrome 配置、已登录 Teams、Git 历史及 GitHub Actions 远端设置。未对真实账号进行动态渗透测试。

## 一、项目概况与依赖

- 平台：Chrome 扩展 Manifest V3，最低 Chrome 120；原生 JavaScript，无 React/Vue/后端服务；IndexedDB 本地数据层；Node ≥20 内置 `node:test`；Python 标准库 `zipfile` 用于打包。
- 入口：`background.js`（Service Worker）、`content.js` / `lib/isolated-reader.js`（隔离的 Teams 缓存读取）、`page-reader.js` / `lib/cache-watch.js`（页面世界的缓存变更提示）、`ui/dashboard.js`、`popup/popup.js`、`overlay/overlay.js`。
- `package.json` 未声明 `dependencies`、`devDependencies`、`optionalDependencies` 或 peerDependencies：**直接第三方依赖 0，间接第三方依赖 0**。无 package-lock、pnpm-lock、yarn.lock、requirements.txt、Pipfile、go.mod、Cargo.toml、pom.xml、Podfile，未发现 vendored npm 库。
- 因为没有第三方依赖，没有可逐一检索 OSV / GitHub Advisory / NVD 的包名和实际安装版本；不编造 CVE。没有可标注为失维护或仿冒的第三方包。
- `npm audit --offline --no-package-lock --json` 显示第三方依赖漏洞条目 0；普通 `npm audit` 无锁文件时不适用。**这一结果不能证明没有代码漏洞。** 官方说明：<https://docs.npmjs.com/cli/commands/npm-audit/>。
- 扩展权限：`storage`, `unlimitedStorage`, `alarms`, `notifications`, `offscreen`, `scripting`；唯一主机权限 `https://teams.live.com/*`，未发现 `<all_urls>`、远程脚本或 `externally_connectable`。权限与现有本地数据、定期巡检、通知、声音和脚本重连功能相关；是否进一步缩减属于功能取舍，未自行更改。

### TGS-UI-SEC-01：请求预览满额导致缓存误报完成 — 已修复

- **根因**：旧逻辑 `const d=project(...); if(d){if(details.length>=20)return;details.push(d);}c.continue();` 在凑满 20 条后遇到第21条有效记录时直接退出 `onsuccess`，没有调用 `cursor.continue()`；IndexedDB 只读事务依然可能正常完成并返回 `status:'OK'`。
- **利用条件**：用户的 Teams 缓存中存在至少21条满足条件的请求会话，且后续还存在待处理请求或需识别为本人发出的会话。攻击者无法仅凭外部网页直接调用扩展后台；需要可影响 Teams 缓存输入或用户实际积累大量请求记录。
- **影响**：后续记录无法被检查，可能遗漏自发消息抑制标记，或漏掉有用的缓存请求线索。**不是**数据被远程窃取，也**不是**自动批准陌生人。
- **修复**：`lib/request-cache.js:64-68` 保留最多20条显示预览，但继续遍历直至自然结束或已有2万条/1.8秒安全上限；不改变预览展示上限、身份匹配、警报规则、权限或存储格式。
- **验证**：`tests/request-cache.test.cjs:40-68` 模拟异步 IndexedDB 游标：前21条外来请求占满预览，末尾还有一个自发消息会话。测试断言预览仍为20条，同时能识别末尾的本人会话键。原来提前返回的逻辑无法满足此断言。

### TGS-UI-SEC-02：本地记录未做额外的静态口令加密 — 待决定

- **利用条件**：其他人已取得同一系统用户的浏览器资料文件、设备被恶意软件读取或用户复制了整个 Chrome Profile。普通网页不能随意访问扩展私有的 IndexedDB。
- **方案A（建议当前保持）**：继续使用浏览器隔离和系统磁盘加密，避免影响无人值守巡检及已存数据；加强使用说明、文件备份保护。
- **方案B**：引入本地数据库口令加密；需定义启动时解锁、后台自动运行、忘记口令、恢复点、旧数据库迁移。需要明确批准及迁移测试，不能悄悄实施。
- **已存在的保护**：用户导出备份使用 WebCrypto PBKDF2-SHA256（250,000轮）、随机盐及随机12字节 IV 的 AES-256-GCM；它不等同于本地数据库静态加密（`ui/dashboard.js:1311-1340`）。

### TGS-UI-SEC-03：缓存观察不等于服务器事实 — 建议关注

- **条件**：离线、缓存残留、主动退群、页面版本升级和读写延迟。
- **风险**：显示的“新增/减少人员”“未标记退出”或历史观察时间，不保证是微软服务器确认的进群、退群或操作时间。代码保持人工核实及不完整名单保护；本次未改变自动退群或人员信任判定。
- **建议**：继续保留界面上的“发现时间”与“待核对”标识；若需要严格实时群数，需先确定合法可靠的官方成员资格数据源并评估支持范围。

### TGS-UI-SEC-04：页面辅助提示非可信 — 建议关注

- **条件**：有脚本已能在 `teams.live.com` 运行，并观察/重放页面内 `postMessage` 携带的会话 nonce。
- **风险**：造成额外的缓存扫描负载，而非直接修改可信人员或从后台取回私人数据。当前 `content.js` 仅把其用作重扫信号，存在约20秒冷却和并发合并；本次没有冒险更换为会破坏 Teams 兼容性的机制。
- **安全依据**：Chrome 官方强调内容脚本传来的消息不应视为完全可信，应限制它能触发的特权动作：<https://developer.chrome.com/docs/extensions/develop/security-privacy/stay-secure>。

### TGS-UI-SEC-05/06：仓库与兼容性盲区 — 待确认/建议关注

- 无 Git 历史和 CI 配置，不能审查提交历史密钥泄漏、`pull_request_target`、第三方 Actions pinning 或发布工作流；请在真实 GitHub 仓库执行额外检查。
- `lib/cache-watch.js` 只监听 Teams 已完成的本地写事务，但会在页面世界包装 `IDBDatabase.prototype.transaction`；目前测试未证明其导致故障，也不能保证 Teams 后续更新永远兼容。若改为完全轮询，会影响实时性和 CPU，先不擅改。

## 五、开发者决策与后续建议

1. **本地静态加密**：先选择 A（现状+设备磁盘加密）或 B（新加密/解锁/迁移）。建议 A，理由是本插件需要后台自动巡检，未经设计的 B 易造成用户数据不可用。
2. **服务端实时成员事实**：若要按真实加入/退出计算，需要先核实可用的官方接口、授权方式和个人版 Teams 支持情况；不要把缓存误差当入侵事件。
3. **仓库及发布链安全**：在完整 Git 仓库和 Actions 配置中补做 Git 历史密钥扫描、依赖与 CI workflow 审核；当前 ZIP 不足以证明从未泄密。
4. **发布前现场验证**：先导出加密备份；在非关键 Teams 账号上测试大量聊天请求、正常监控、退群和批量核对；确保 Chrome 是从本次修复目录加载，而不是仍运行旧 Service Worker。

**说明**：这是按可获取源码完成的静态审核和本地自动测试，不是已登录 Microsoft Teams 的真实环境渗透测试；没有凭空标注 CVE，也没有对未验证漏洞作确定性宣称。
