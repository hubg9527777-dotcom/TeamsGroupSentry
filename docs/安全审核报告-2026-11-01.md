### TSG-SEC-01：Unicode 不可见字符可能误导身份核对 — 已修复

- **原因与利用条件：** Teams 群成员资料、联系人资料或缓存记录中，名字包含 U+202E、U+200B 等显示控制字符，或 ID 内混入看不见的格式字符。此前部分 `cleanName()` 只进行 trim 截断；`personId()` / `threadId()` 的字符限制也未覆盖所有方向与零宽字符。相似的视觉显示可能使人工误判两个不同的身份标识。攻击者必须能够影响插件读取的 Teams 姓名或缓存，不能凭此直接通过成员审核。
- **影响：** 审核界面的视觉身份混淆；并非已证明绕过审批或跨账号访问。
- **改动：** `lib/logic.js:6-11` 和 `lib/name-core.js:7-12` 对姓名中的不可见格式字符做显示清理；对人员 ID、群 ID 的同类字符拒绝接收。保留合法中文、拉丁文及正常 Teams ID；不修改已保存记录、不自动审核身份。
- **验证：** `tests/security-hardening.test.cjs:6-23` 验证混入零宽/方向控制符的人员和群 ID 被拒绝，正常 ID 与姓名仍可使用。

### TSG-SEC-02：头像姓名查找在超大群中存在平方级成本 — 已修复

- **原因与利用条件：** 旧 `parseRecord()` 为每个成员调用 `findName(member, avatars)`，最多遍历 3,000 个成员 × 3,000 个头像记录。成员列表较大且姓名缺失时，可能造成重复约 900 万次头像匹配，影响页面巡检响应；需要 Teams 本地缓存提供大规模数据。
- **影响：** 可用性 / CPU 消耗，未发现能直接越权或泄露数据的路径。
- **改动：** `lib/logic.js:53-66` 先建立以**完整成员 ID**索引的 `Map`，再逐成员查询，将头像匹配由 O(N×M) 改为约 O(N+M)；保留成员自身资料优先、只有精确 ID 相同才补名、相同 ID 取第一个有效姓名的旧行为。
- **验证：** `tests/security-hardening.test.cjs:25-49` 用 3,000 人、重复头像、跨人员资料验证姓名不会串到其他 ID。

### TSG-SEC-03：本地数据库以浏览器配置文件原生方式保存 — 待开发者决定

- **利用条件：** 攻击者已获得操作系统用户文件访问能力、用户使用共享 Chrome 配置文件、或某个本地备份包含未经加密的浏览器资料数据；普通网页无法直接读取扩展私有数据库。
- **风险：** 群成员姓名、ID、审核历史可能被本地文件读取者接触。导出的独立备份使用 PBKDF2-SHA256（250,000 次）和随机盐/IV 的 AES-256-GCM；这不代表 IndexedDB 静态数据也受到同样加密。
- **方案 A（建议默认）：** 保持现有本地存储，依赖操作系统账户和磁盘加密，明确提示勿分享 Chrome 配置目录；零迁移风险。
- **方案 B：** 新增本地数据库口令加密与解锁。需要讨论口令管理、浏览器后台自动运行、恢复、忘记密码和旧数据迁移；**未经明确批准不实施**。

### TSG-SEC-04：成员资格的实时准确性不是缓存能够保证的 — 建议关注

- **利用条件：** Teams 缓存延迟、离线、群聊退出或页面异步更新。
- **风险：** 如果用户将本地缓存数量误当服务器实时群数，可能得到错误的安全判断。项目已有只读保护、不完整名单保护和人工核查；本次没有修改业务判定。
- **建议：** 继续在 UI 中明确区分“已记录/未标记退出”和“服务器实时成员资格”，不得以缓存缺少某人直接自动批准、自动删除或将其标记成真实退群。

### TSG-SEC-05：页面 MAIN 世界提示属于非可信的辅助信号 — 建议关注

- **利用条件：** 有恶意脚本已能在 `teams.live.com` 页面执行，并监听或重放 `window.postMessage` 里的 nonce。
- **风险：** 触发额外缓存读取，造成有限的性能消耗。此提示不携带群成员或凭证，真正的 ID 和名单来自 ISOLATED 读取器；事件读取有约 20 秒冷却、任务合并，不能直接写入成员信任数据。
- **建议：** 保留严格频率限制；若将来显著提高后台读取频率或允许 MAIN 世界消息写入审核状态，必须重新安全审查。

### TSG-SEC-06：仓库外部发布链无法由 ZIP 验证 — 待确认

- **具体限制：** 压缩包没有 `.git` 历史、远端 CI YAML、GitHub Actions 配置或部署令牌，无法验证是否曾在提交历史泄漏凭据，也无法判断 CI 是否使用 `pull_request_target`、未锁定的 Action 等。
- **开发者下一步：** 在实际 GitHub 仓库运行 secret scanning，并检查提交历史 / Actions / Release 工作流。不得把“本次 ZIP 未发现密钥”解读为“所有历史版本从未泄密”。
